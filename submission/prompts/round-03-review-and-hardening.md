# 第 3 轮：以评委视角评审并落地改进

- 轮次：3
- 场景：两个作品可运行后，要求 AI 切换到评委视角挑问题，并只保留可落地的改进
- 使用的 AI：Trae 内置 AI 助手（对话式）

## 用户原始输入（逐字）

第一条：

> 你现在是比赛评委，你觉得这两个产品还有哪些可以优化的点？有哪些还做得不够好的地方

第二条（评审后选择执行项）：

> 先建 Git 仓库并提交代码

第三条（决定并行推进两类工作）：

> 都要，并行操作

## AI 评审结论（要点）

按「AI 创新深度 / 功能完整度 / 实用价值 / 技术质量 / 演示冲击」五维打分，两产品均在 6 分区间，并指出：

- RunLedger：统计严谨性不足，只有信号噪声比阈值，没有置信区间；产品定位与演示亮点不够。
- 送货单：AI 只有单次调用，缺少字段校验与缺失提示；「解析错了怎么办」缺闭环。
- 共同硬伤：没有 Git 提交历史、没有单元测试。

## 未采纳的建议（如实记录）

- OCR 拍照识别：需要视觉模型，时限内无法稳定完成，明确不做。
- 多模板、多人协作、云端同步：超出最小可演示范围，不做。
- 重构 `Dashboard.tsx` / `Views.tsx`：两产品共用逻辑已稳定，重构风险大于收益，不做。

## 验证方式

- 每项改动后执行 `npm run typecheck` 与 `npm run build`，并用无头浏览器读取三个页面控制台，确认 0 error。
- 置信区间为描述性区间，文案中明确不用于显著性判定，避免把展示值包装成统计检验结论。
